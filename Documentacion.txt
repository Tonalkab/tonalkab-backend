🔐 Documentación – Implementación de Autenticación JWT
Proyecto Tonalkab

1. Introducción
En esta fase del desarrollo se implementó un sistema completo de autenticación basado en JSON Web Tokens (JWT) para el backend del proyecto Tonalkab.
El objetivo es permitir autenticación segura, manejo de sesiones sin estado y protección de endpoints, siguiendo buenas prácticas utilizadas en sistemas backend modernos.

2. Concepto de JWT
JWT (JSON Web Token) es un mecanismo de autenticación basado en tokens firmados que contienen información del usuario.
El flujo general es:
Login → Generación de token → Cliente guarda token → Requests autenticados
El token incluye información como:
	• Identificador del usuario (sub)
	• Fecha de expiración (exp)
Este token es firmado mediante una clave secreta, garantizando su integridad.

3. Arquitectura de Autenticación
La arquitectura implementada es la siguiente:
App móvil → Login → Backend genera JWT
↓
App almacena token
↓
App envía token en cada request
↓
Backend valida token y permite acceso
Esto elimina la necesidad de manejar sesiones en el servidor.

4. Configuración del Sistema
Se definieron variables de entorno para la configuración de JWT:
JWT_SECRET_KEY
JWT_ALGORITHM
JWT_EXPIRE_MINUTES
Estas variables permiten desacoplar la configuración de seguridad del código fuente.

5. Implementación en el Backend
5.1 Centralización en security.py
El archivo core/security.py se convirtió en el módulo central de seguridad del sistema.
Incluye:
	• Hash de contraseñas (bcrypt)
	• Verificación de contraseñas
	• Generación de tokens JWT
	• Validación de tokens
Esto mantiene una arquitectura limpia y escalable.

5.2 Generación de Token
Se implementó una función para generar tokens:
	• Recibe datos del usuario
	• Agrega expiración
	• Firma el token con SECRET_KEY
	• Devuelve el token codificado
Se utiliza el estándar:
sub → identificador del usuario

5.3 Validación de Token
Se implementó una función para verificar tokens:
	• Decodifica el token
	• Valida firma y expiración
	• Extrae el user_id desde "sub"
	• Retorna el identificador del usuario
Si el token es inválido o expirado, se rechaza.

6. Modificación del Endpoint de Login
El endpoint /login fue actualizado para:
	• Validar credenciales
	• Generar JWT
	• Retornar token en formato estándar
Formato de respuesta:
{
"access_token": "TOKEN",
"token_type": "bearer"
}
También se mejoró la seguridad:
	• Uso de código HTTP 401
	• Mensaje genérico para evitar filtración de información

7. Autenticación en Requests
El cliente debe enviar el token en cada request mediante el header:
Authorization: Bearer
Este header es interceptado por el backend para validar la autenticación.

8. Obtención de Usuario Autenticado
Se implementó la función get_current_user como dependencia de FastAPI.
Su funcionamiento:
	• Extrae el token del header
	• Verifica el token
	• Obtiene el user_id
	• Consulta el usuario en la base de datos
	• Retorna el objeto usuario
Esto permite inyectar automáticamente el usuario autenticado en cualquier endpoint.

Ejemplo:

Documentación Técnica: Resolución de Errores y Estabilización - Proyecto Tonalkab (Backend)
📌 Resumen Ejecutivo
Durante la configuración del entorno de desarrollo local y producción del sistema Tonalkab (FastAPI + MySQL + Docker), se identificaron y resolvieron una serie de fallos en cascada. Estos incluyeron conflictos de red, condiciones de carrera (tiempos de arranque de contenedores), mala estructuración de paquetes en Python y omisión de dependencias críticas. El entorno ahora es 100% estable y replicable.

🛑 Fase 1: Problemas de Infraestructura y Orquestación (Docker)
1.1 Conflicto de Puertos en Desarrollo (Port is already in use)
	• Síntoma: Al ejecutar docker compose up, Docker arrojaba un error indicando que el puerto 8000 ya estaba ocupado.
	• Causa Raíz: El archivo docker-compose.yml (base) exponía el puerto 127.0.0.1:8000:8000 por seguridad en el VPS. El archivo local docker-compose.override.yml intentaba añadir 8000:8000. Docker Compose V2, por defecto, "suma" los puertos en lugar de reemplazarlos, causando un choque consigo mismo.
	• Solución: Se implementó la etiqueta personalizada !override en el archivo de desarrollo para forzar a Docker a ignorar la configuración del archivo base.
YAML

# docker-compose.override.yml
services:
  backend:
    ports: !override
      - "8000:8000"
1.2 Caída del Backend por Desincronización (Crash Loop / Error 111)
	• Síntoma: El contenedor tonalkab_backend se reiniciaba infinitamente. Los logs mostraban Can't connect to MySQL server on 'db' ([Errno 111] Connection refused).
	• Causa Raíz: El contenedor de FastAPI arrancaba en milisegundos e intentaba conectarse a MySQL. Sin embargo, el motor InnoDB de MySQL tarda unos 10-15 segundos en inicializarse y estar listo para recibir conexiones. Al fallar la conexión, Python lanzaba una excepción fatal.
	• Solución: Se implementó un healthcheck en el servicio de la base de datos y se configuró el backend con una espera activa condicionada.
YAML

# docker-compose.yml
services:
  backend:
    depends_on:
      db:
        condition: service_healthy
  db:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 5

🛑 Fase 2: Problemas Estructurales de Python y FastAPI
2.1 Fallos de Importación Absoluta (ModuleNotFoundError)
	• Síntoma: Los logs del backend mostraban ModuleNotFoundError: No module named 'app.models.auth_provider'.
	• Causa Raíz: El Dockerfile original usaba un comando RUN pip install ... en línea muy largo y no definía el contexto de ejecución para que Python encontrara la carpeta /app como un módulo raíz válido. Además, faltaban los archivos inicializadores de paquetes.
	• Solución: 1. Se crearon archivos __init__.py vacíos en todas las subcarpetas de app/. 2. Se optimizó el Dockerfile para usar un archivo requirements.txt (mejorando la caché) y se añadió la variable global PYTHONPATH.
Dockerfile

# Dockerfile Optimizado
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ENV PYTHONPATH=/app
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
2.2 Código y Lógica Faltante (Google Auth)
	• Síntoma: A pesar de arreglar las rutas, el error mutó a ImportError: cannot import name 'AuthProvider'.
	• Causa Raíz: Al revisar el código fuente, se detectó que el desarrollador había programado el endpoint de login con Google (@router.post("/auth/google")) en auth.py, pero había olvidado crear los archivos físicos que daban soporte a esa lógica.
	• Solución: Se programaron y crearon los 3 bloques de código faltantes:
		1. El Modelo: Se creó app/models/auth_provider.py con la clase AuthProvider en SQLAlchemy.
		2. El Validador: Se creó app/core/google_auth.py con la función verify_google_token.
		3. El Esquema: Se añadió GoogleAuthRequest al archivo app/schemas/auth.py.

🛑 Fase 3: Dependencias Ocultas
3.1 La Librería "Fantasma" de Google
	• Síntoma: El último error registrado fue ModuleNotFoundError: No module named 'requests'.
	• Causa Raíz: La librería oficial google-auth (usada para validar los tokens de sesión) depende internamente de la librería requests para hacer llamadas HTTP a los servidores de Google. Esta dependencia no venía incluida por defecto.
	• Solución: Se añadió explícitamente requests a la lista de dependencias del proyecto.

from fastapi import HTTPException

def verify_google_token(token: str):

Campos clave: humedad_suelo_min, humedad_suelo_max, tiempo_min_entre_riegos_dias, modo_operacion.

tipo_activacion: Define el origen del riego (Botón físico, sensor crítico o forzado por IA).

estado_registro: Monitorea el éxito o fallo de la transacción de riego.

Se desarrollaron los puntos de entrada para la comunicación de alta eficiencia con los dispositivos.

Propósito: Entrega al hardware su "hoja de ruta" operativa.

Lógica interna: Realiza un cruce de datos (Join) entre la biología de la planta, las preferencias del usuario y la última dosis calculada por la IA.

Respuesta: Un objeto JSON que incluye umbrales de humedad, dosis en mililitros y el tiempo transcurrido desde el último riego exitoso.

4. Lógica de Negocio e Inteligencia Vegetal
Se estableció un motor de decisiones híbrido basado en tres pilares:

Humedad Crítica: Prioridad absoluta. Si el suelo baja del mínimo biológico, se activa el riego independientemente del tiempo transcurrido.

Ciclo de Tiempo (Timeout): Si se cumple el tiempo de espera configurado, el sistema evalúa la humedad. Si no es óptima (pero no crítica), se aplica un riego de mantenimiento.

Dosis Dinámica (ML Injection): La cantidad de agua no es fija; el backend inyecta en el objeto de configuración una dosis calculada por IA, optimizando el recurso hídrico según el histórico de la planta.

JWT (JSON Web Tokens): Para la gestión de usuarios y acceso desde la plataforma móvil.

API Keys con Hashing (SHA-256): Para los dispositivos. El servidor valida tokens planos enviados por el hardware comparándolos con el hash almacenado en la base de datos, garantizando que el acceso al /config sea exclusivo para dispositivos registrados.

Documentación Técnica: Algoritmo de  (Valle a Pico)
Descripción General El algoritmo de "Valle a Pico" es un mecanismo de detección de anomalías hídricas ejecutado en el backend. Su propósito es identificar aumentos de humedad en la tierra que no fueron provocados por el sistema de riego autónomo (por ejemplo, lluvia o riego manual), aislar estos eventos para proteger el modelo de Machine Learning y evitar el desperdicio de agua en el siguiente ciclo del hardware.

1. El Problema a Resolver (Tasa de Percolación)
El agua no penetra la tierra de forma instantánea. Si llueve, la humedad del sustrato sube gradualmente a lo largo de varios minutos. Un sistema básico que solo compara la "lectura actual" contra la "lectura del minuto anterior" fallaría en detectar la tormenta, ya que los incrementos minuto a minuto son muy pequeños (ej. 1% o 2%).
Para resolver esto, el algoritmo no analiza puntos aislados, sino Ventanas de Tiempo.

2. División de Responsabilidades (Edge vs. Nube)
Para mantener la eficiencia y la separación de capas en la arquitectura de Tonalkab, el proceso se divide estrictamente:
	• El ESP32 (Hardware - Testigo Ciego): No realiza ningún cálculo relacionado con el clima. Su única responsabilidad es leer los sensores físicos con la frecuencia establecida y enviar los datos "crudos" al servidor. No sabe si el agua que detecta es de lluvia o de su propia bomba.
	• El Servidor (Backend - Cerebro Analítico): Recibe los datos crudos, revisa el historial reciente de la base de datos, ejecuta las comparaciones matemáticas de la ventana de tiempo y emite un veredicto. Si detecta lluvia, manipula la base de datos para registrar el evento.

3. Lógica del Algoritmo Paso a Paso
El algoritmo se ejecuta en el endpoint de telemetría (POST /devices/lecturas) cada vez que el ESP32 envía un nuevo dato.
	1. Definición de la Ventana: El servidor retrocede 15 minutos en el tiempo desde el momento actual.
	2. Búsqueda del "Valle": Consulta en la base de datos cuál fue el nivel de humedad más bajo registrado dentro de esos 15 minutos.
	3. Cálculo del "Pico": Calcula la diferencia (Delta) restando el Valle a la lectura de humedad recién recibida.
	4. Cruce de Umbral: Evalúa si el Delta es superior al 8%. (Este umbral indica que la tierra recibió una cantidad significativa de agua).
	5. Descarte de Falsos Positivos: Si el Delta es mayor al 8%, el servidor verifica la tabla control_riego. Si descubre que la bomba de agua del dispositivo se encendió en esos mismos 15 minutos, ignora el evento (fue un riego normal). Si la bomba no se encendió, se confirma la anomalía: es lluvia.
	6. Sistema Anti-Rebote: Para evitar que una tormenta continua genere decenas de registros duplicados por cada lectura nueva que llega, el servidor verifica si ya registró un evento de lluvia en los últimos 15 minutos. Si ya existe, simplemente actualiza o ignora; si no existe, crea un único registro oficial.

4. Impacto en el Sistema (Cierre del Ciclo)
La detección exitosa de lluvia desencadena dos acciones críticas en la plataforma:
	• Ahorro Hídrico Inmediato: Al crear el registro de "Lluvia Exitosa", el reloj interno del servidor se reinicia. Al día siguiente, cuando el ESP32 descargue sus reglas operativas, verá que han pasado "0 días" desde el último riego y cancelará cualquier orden de encender la bomba, ahorrando el agua del tanque.
	• Limpieza del Dataset: Al etiquetar este evento explícitamente como "Lluvia" (id_tipo_activacion = 4), los futuros algoritmos de Machine Learning podrán filtrar esta fila. Esto evita que la Inteligencia Artificial asuma erróneamente que la maceta ganó 20% de humedad sin haber gastado ni un mililitro de agua de la bomba.


Documentación Técnica: Sistema de Gestión Edge y Resiliencia Hídrica
1. Gestión Autónoma de Conectividad (Heartbeat Activo)
Se implementó un sistema de monitoreo de salud del hardware (Health Check) en el servidor para garantizar que el estado de los dispositivos en la base de datos sea verídico sin depender de la interacción del usuario.
	• Componente: app/core/tasks.py y app/main.py.
	• Lógica de Operación: * El servidor ejecuta una tarea asíncrona en segundo plano cada 2 minutos.
		○ Se definió un umbral de tolerancia de 5 minutos.
		○ Si una maceta no envía datos en ese lapso, el sistema marca automáticamente la conexión como desconectada y cambia el estado global de la maceta a inactivo.
	• Beneficio: Elimina falsos positivos de "dispositivo en línea" y permite generar alertas de mantenimiento si un sensor pierde energía o señal Wi-Fi.

2. Algoritmo "Valle a Pico" de Doble Capa
Se evolucionó la detección de lluvia para capturar no solo eventos climáticos drásticos, sino también precipitaciones ligeras y prolongadas (lloviznas) que afectan la humedad del suelo.
	• Componente: app/api/device.py (Endpoint /lecturas).
	• Capas de Análisis:
		1. Ventana Rápida (15 min): Detecta incrementos repentinos superiores al 8%. Ideal para aguaceros o riego manual con jarra.
		2. Ventana Lenta (60 min): Detecta incrementos acumulados superiores al 12%. Diseñado para lloviznas que saturan el suelo gradualmente pero que el radar de 15 minutos podría ignorar.
	• Filtro de Falsos Positivos: El sistema cruza el incremento de humedad con el estado de la bomba. Si hubo aumento de humedad pero la bomba estuvo apagada, se registra oficialmente como "Evento de Lluvia" (id_tipo_activacion = 4).
	• Beneficio: Ahorro hídrico al evitar riegos innecesarios tras una lluvia y garantiza que el dataset para Machine Learning no contenga ruido (incrementos de humedad "fantasma").

3. Arquitectura de Configuración Híbrida (Edge Computing)
Se optimizó el intercambio de reglas operativas para que el ESP32 sea capaz de tomar decisiones locales sin consultar al servidor en cada segundo.
	• Flujo de Datos: El dispositivo descarga mediante GET /config un paquete JSON que contiene:
		○ Umbrales Biológicos: Humedad mínima y máxima según el tipo de planta o configuración manual.
		○ Dosis Dinámica: La cantidad de mililitros a regar, calculada por el modelo de IA o por reglas de negocio.
		○ Calibración de Hardware: El flujo real de la bomba (ml/s).
	• Beneficio: Autonomía del hardware. Si el Wi-Fi falla, el ESP32 ya conoce sus límites y puede seguir operando de forma segura.

4. Herramientas de Validación (Simulador ESP32)
Para garantizar la integridad de la integración Hardware-Software, se desarrolló un firmware de simulación interactiva.
	• Capacidades:
		○ Simulación de Eventos: Permite disparar manualmente estados de "Humedad Baja" y "Salto de Humedad (Lluvia)" para observar la respuesta del backend en tiempo real.
		○ Auditoría de Transacciones: Valida que cada reporte de riego genere el descuento correcto en los cálculos de agua y actualice los registros históricos de la planta.
Uso en Pruebas: Permite estresar el sistema y validar la base de datos sin necesidad de mojar sensores físicos durante la etapa de desarrollo de software.

📑 Documentación Técnica: Sistema de Alertas Reactivas

### 1. Filosofía del Diseño: "Monitorización sin Ruido"

El objetivo principal de este módulo es notificar al usuario sobre condiciones críticas (humedad, batería, agua) garantizando la limpieza de la base de datos. Se implementó una lógica de **Anti-Spam** que evita la duplicidad de alertas: si una condición crítica persiste, el sistema solo mantiene una alerta activa hasta que el usuario la marque como "vista" o se resuelva el problema.

### 2. Arquitectura de Datos (Modelos SQLAlchemy)

Se implementaron las entidades siguiendo la estructura de normalización definida en el diccionario de datos:

- **Entidad Alerta**: Almacena el mensaje, la maceta origen, el timestamp y los estados de visualización.
    
- **Catálogo TipoAlerta**: Clasifica los eventos en: `baja_humedad` (1), `bateria_baja` (2), `desconexion` (3) y `nivel_agua_bajo` (4).
    
- **Catálogo PrioridadAlerta**: Define la urgencia como `baja` (1), `media` (2) o `alta` (3).
    
- **Catálogo EstadoAlerta**: Gestiona el ciclo de vida de la notificación: `pendiente` (1), `vista` (2) o `resuelta` (3).
    

### 3. Lógica de Gatillos (Triggers) en Telemetría

La detección de alertas se integró directamente en el flujo de recepción de datos del hardware (`POST /devices/lecturas`). El sistema realiza las siguientes comparaciones en cada reporte del ESP32:

|**Variable**|**Condición de Disparo**|**Prioridad**|
|---|---|---|
|**Humedad del Suelo**|Menor al umbral mínimo biológico o manual configurado.|Alta (3)|
|**Voltaje de Batería**|Valor inferior a 3.3V (Límite crítico de operación).|Media (2)|
|**Nivel de Agua**|Depósito por debajo del 10% de su capacidad.|Alta (3)|

### 4. Interfaz de Programación (API)

Se expusieron endpoints específicos para la interacción con la aplicación móvil en React Native:

- **`GET /macetas/{id}/alertas`**: Permite a la App obtener las notificaciones activas. Soporta el parámetro `solo_pendientes` para optimizar el tráfico de red.
    
- **`PATCH /alertas/{id}/vista`**: Endpoint de confirmación. Cambia el estado de la alerta y la marca como leída por el usuario, permitiendo que el sistema pueda generar una nueva alerta si la condición crítica se repite en el futuro.

🧠 Documentación Técnica: Inyección de Machine Learning y Estabilización de Entorno (Docker)
Proyecto: Tonalkab

1. Resumen de la Fase
En esta fase se logró el hito de convertir a Tonalkab de un sistema de monitoreo reactivo a un sistema inteligente y predictivo. Se integró exitosamente un modelo de Machine Learning (Random Forest Regressor) en el backend para predecir dosis milimétricas de riego, resolviendo simultáneamente problemas críticos de compatibilidad de binarios en el contenedor de despliegue.

2. Arquitectura de Inferencia Asíncrona (FastAPI BackgroundTasks)
Para garantizar que la inyección de Inteligencia Artificial no penalizara los tiempos de respuesta (latencia) del hardware ESP32, se implementó un patrón de diseño de Ejecución en Segundo Plano.

Punto de Disparo (Gatillo): La IA se invoca dentro del endpoint de telemetría (POST /devices/lecturas).

Mecanismo: Se inyectó el módulo BackgroundTasks de FastAPI. Cuando el ESP32 reporta sus sensores, el servidor le responde inmediatamente con un 200 OK ("Lectura guardada"). Inmediatamente después y de forma silenciosa, el servidor arranca el proceso matemático pesado para predecir el futuro.

Beneficio: Evita cuellos de botella en la red y asegura que el hardware vuelva a dormir o a ejecutar sus rutinas locales lo más rápido posible.

3. Módulo de Inferencia (app/ml/inference.py)
Se creó un nuevo módulo dedicado exclusivamente a interactuar con el modelo predictivo.

Carga del Cerebro: El sistema utiliza la librería joblib para cargar en memoria el archivo pre-entrenado modelo_riego_tonalkab.pkl.

Contextualización: El script consulta la tabla LecturaSensores para obtener el estado actual de la maceta y cruza este dato con los umbrales biológicos definidos en ConfiguracionMaceta o TipoPlanta para calcular el Delta de humedad requerido.

Persistencia: La predicción final (en mililitros) se guarda automáticamente en la tabla predicciones_ml con el identificador dosis_riego, quedando a la espera de ser consumida por el hardware.

4. Cierre del Ciclo Edge Computing
La predicción calculada por la nube se entrega al ESP32 a través del endpoint operativo:

Ruta: GET /devices/config

Lógica de Entrega: El endpoint busca la predicción más reciente (y con una confianza_modelo superior al 80%) y la empaqueta en la variable dosis_ml_calculada.

Calibración Física: Se definió la variable flujo_bomba_ml_por_segundo = 15.0 (configurable), la cual actúa como el "traductor" entre el volumen líquido calculado por la IA (ml) y el tiempo físico que el ESP32 debe encender su relé (milisegundos).

5. Estabilización del Entorno de Producción (Resolución de Bugs)
Durante la inyección de las librerías de Data Science (pandas, scikit-learn, joblib), el contenedor Docker colapsó impidiendo el arranque de uvicorn.

🛑 El Problema (C-API Incompatibility):

Error: ValueError: numpy.dtype size changed, may indicate binary incompatibility. Expected 96 from C header, got 88 from PyObject

Causa Raíz: Las dependencias instalaron automáticamente la última versión disponible de la librería matemática numpy (v2.0+). Esta nueva versión principal cambió drásticamente su arquitectura en C, rompiendo la compatibilidad interna con la versión de pandas (2.1.0) que el sistema utilizaba.

✅ La Solución (Dependency Pinning):
Se aplicó un parche estricto en el archivo docker/requirements.txt para congelar (pinning) la versión matemática a la última rama estable de la generación 1.x.

Configuración Final y Segura:

Plaintext
pandas==2.1.0
scikit-learn==1.3.0
joblib==1.3.2
numpy==1.26.4
Tras reconstruir el contenedor (docker compose up -d --build), el problema de binarios quedó resuelto permanentemente, garantizando la estabilidad del entorno de FastAPI tanto en desarrollo (Windows) como en producción (Debian VPS).

🎯 Resumen Ejecutivo
Se ha implementado una arquitectura de doble capa (Nube + Edge) para la gestión del riego automatizado. El sistema ahora utiliza un modelo de Machine Learning (Random Forest) que aprende la capacidad de absorción específica de cada sustrato basándose en su historial. Además, se ha dotado al microcontrolador ESP32 de una lógica de Edge Computing que garantiza la autonomía de la maceta incluso frente a caídas prolongadas de la red WiFi.

🧠 1. Machine Learning: Aprendizaje por Historial y Cold Start
El algoritmo ya no solo reacciona a variables climáticas, sino que comprende la física del suelo de cada usuario.

Problema resuelto (Cold Start): Para evitar que el sistema sea ineficiente el día 1, se desarrolló un simulador que genera un dataset inicial con diferentes perfiles de sustrato (arcillosos, arenosos, mixtos) afectados por el clima.

Nueva Variable (Feature Engineering): Se introdujo la tasa_absorcion_historica. El modelo ahora entiende cuántos mililitros de agua le toma históricamente a esa maceta en específico subir un 1% su nivel de humedad.

Archivo Implementado: app/ml/train_model.py (Script de generación de datos sintéticos y entrenamiento de Scikit-Learn que exporta el archivo .pkl v2).

⚙️ 2. Motor de Inferencia en Backend (FastAPI)
El servidor ahora procesa y digiere los datos transaccionales antes de consultar a la Inteligencia Artificial.

Cálculo Dinámico: Antes de predecir la dosis, el backend consulta la tabla ControlRiego. Extrae los últimos 5 riegos exitosos de la maceta y calcula la media matemática de su eficiencia real (mililitros_inyectados / porcentaje_incrementado).

Precisión Quirúrgica: El modelo predice la dosis exacta en mililitros basándose en el delta necesario (Humedad Objetivo - Humedad Actual), evitando el desperdicio de agua y, por ende, optimizando la energía de la biobatería y panel solar.

Archivo Implementado: app/ml/inference.py (Actualizado para procesar 5 variables de entrada hacia el Random Forest).

📡 3. API y Comunicación con el Hardware (IoT)
La API se ha modificado para que el servidor no solo reciba datos, sino que configure al microcontrolador para actuar de forma autónoma.

Transmisión de Inteligencia: El endpoint GET /devices/config calcula la Tasa de Absorción Histórica y se la envía al ESP32 en el objeto JSON bajo la llave tasa_absorcion_ml_por_porcentaje.

Evaluación de Anomalías (Lluvia): El endpoint de recepción de lecturas (POST /devices/lecturas) evalúa ventanas de tiempo (15 y 60 minutos). Si detecta un incremento de humedad sin que la bomba se haya encendido, registra un evento de lluvia para no desfasar el modelo de IA.

Asincronía: El entrenamiento y la inferencia se envían a hilos secundarios (BackgroundTasks) para no bloquear la respuesta HTTP al microcontrolador.

Archivos Implementados: * app/schemas/device.py (Validación con Pydantic del nuevo parámetro).

app/api/device.py (Endpoints refactorizados con cálculos históricos).

🔌 4. Especificaciones para el Firmware (ESP32 en C++)
Para que esta arquitectura se complete, el equipo de hardware debe implementar la siguiente lógica en el ESP32:

Persistencia de Datos: Al consumir el endpoint /config, el ESP32 debe extraer el valor tasa_absorcion_ml_por_porcentaje y guardarlo en la memoria no volátil (se recomienda usar la librería <Preferences.h>).

Modo Offline (Resiliencia): Si WiFi.status() != WL_CONNECTED y los sensores indican humedad baja, el ESP32 debe ejecutar el riego utilizando la matemática guardada en memoria:

Fórmula: ml_necesarios = (humedad_max - humedad_actual) * tasa_guardada

Traducción a Hardware: tiempo_bomba_segundos = ml_necesarios / 15.0 (suponiendo un flujo de 15ml/s).

Retraso de Lectura (Delay de Absorción): Tras ejecutar un riego físico, el hardware debe esperar aproximadamente 10 a 15 minutos antes de tomar la lectura final y hacer el POST /devices/riego. Esto garantiza que el agua haya bajado al sensor y los datos de retroalimentación para la IA sean correctos.

💡 Puntos Clave para la Defensa del Proyecto
Eficiencia Computacional: Al pasar la "regla de tres" al hardware para el modo offline, se reduce la carga computacional en el ESP32, ahorrando batería.

Escalabilidad: El uso de BackgroundTasks en FastAPI permite que un solo servidor VPS maneje miles de macetas sin colapsar.

Sostenibilidad: El cruce de variables ambientales con el perfil del sustrato asegura que Tonalkab utilice exactamente la cantidad de agua y energía de bombeo estrictamente necesarias, haciendo viable el modelo de energía híbrida por oxidación de metales.

🎯 Resumen de la Actualización
Se aplicó una refactorización integral orientada a la alta disponibilidad, rendimiento en redes celulares, protección de infraestructura frente a abusos y control formal de cambios de base de datos en producción.

---

### 🛡️ A. Resiliencia de Conexiones a Base de Datos (SQLAlchemy Connection Pool)
- **Problema:** En servidores con MySQL, conexiones inactivas eran cerradas por timeout (`wait_timeout`), arrojando errores "MySQL server has gone away".
- **Solución implementada (`backend/app/db.py`):**
  - `pool_size=10`: Mantiene hasta 10 conexiones persistentes listas en memoria.
  - `max_overflow=20`: Permite picos de hasta 30 conexiones simultáneas sin colapsar.
  - `pool_recycle=3600`: Renueva conexiones cada hora antes de que MySQL las interrumpa.
  - `pool_pre_ping=True`: Verifica la salud de la conexión con un "ping" antes de ejecutar consultas.

---

### ⚡ B. Eliminación de Consultas N+1 (Endpoint Unificado de Dashboard)
- **Problema:** La pantalla principal de la app móvil realizaba 1 petición a `/macetas/`, 1 a `/catalogos/plantas` y N peticiones adicionales a `/macetas/{id}/lecturas/actual`. En un huerto de 5 macetas, esto generaba 7 viajes de red lentos.
- **Solución implementada (`backend/app/api/maceta.py` y `backend/app/schemas/maceta.py`):**
  - Nuevo endpoint: `GET /macetas/dashboard`.
  - Entrega en una sola respuesta JSON consolidada:
    - Datos generales de la maceta.
    - Ficha botánica completa de `TipoPlanta` (umbrales ideales).
    - Última medición registrada en `LecturaSensores`.
    - Skin activa configurada (`SkinBase`).
    - Estado de red en tiempo real (`ConexionResponse`), indicando si está conectada o desconectada según el cálculo de inactividad (>5 min).
- **Impacto Frontend (`tonalkab/src/screens/HomeScreen.js`):** La app móvil ahora carga su pantalla principal en una sola petición HTTP ultrarrápida.

---

### 🛑 C. Rate Limiting y Protección contra Abusos (SlowAPI)
- **Módulo (`backend/app/core/limiter.py` y `backend/app/main.py`):**
  - Integración de `slowapi` con limitación basada en IP cliente (`get_remote_address`).
- **Rutas Protegidas:**
  - `POST /login` (`backend/app/api/auth.py`): **5 peticiones / minuto** (Mitigación de ataques de fuerza bruta en contraseñas).
  - `POST /bot/chat` (`backend/app/api/bot.py`): **15 peticiones / minuto** (Protección de cuotas de tokens y costos en Gemini y Groq).
- **Respuesta:** En caso de superar el umbral, el servidor responde con HTTP `429 Too Many Requests`.

### 🏗️ CONTEXTO DE INFRAESTRUCTURA Y CIBERSEGURIDAD: SERVIDOR TONALKAB
Propósito: Este documento describe la arquitectura actual, las reglas de firewall, la contenerización y el enrutamiento del servidor de producción para el proyecto "Tonalkab". Cualquier código o sugerencia generada debe respetar estrictamente estos lineamientos de seguridad.

1. Servidor Base y Hardening (Debian 13)
El servidor es un VPS corriendo Debian 13 (Testing). Se ha priorizado la reducción de la superficie de ataque mediante las siguientes configuraciones de sistema:

Administración de Usuarios: El acceso mediante la cuenta root está completamente prohibido (PermitRootLogin no). Toda la administración se realiza a través del usuario personal tonalkab, el cual cuenta con privilegios sudo.

Seguridad SSH: El demonio SSH (/etc/ssh/sshd_config) fue reconfigurado para escuchar en el puerto no estándar 2022, evadiendo escaneos automatizados. Solo se permite el acceso mediante llaves criptográficas (PubkeyAuthentication yes), estando la autenticación por contraseña desactivada.

Firewall (UFW): Opera bajo una política estricta de "Denegar por defecto" (default deny incoming). Los únicos puertos abiertos hacia internet son:

2022/tcp (SSH Administrativo)

80/tcp (HTTP - Solo para redirección a HTTPS)

443/tcp (HTTPS - Tráfico cifrado de la API)

2. Blindaje del Ecosistema Docker
El entorno ejecuta contenedores gestionados mediante docker-compose.yml. Para corregir la vulnerabilidad donde Docker manipula iptables y expone puertos ignorando a UFW, se ha implementado la utilidad ufw-docker. Ningún contenedor es accesible desde internet a menos que sea explícitamente enrutado a través del proxy inverso en el host.

Servicios de Docker Compose:
Backend (FastAPI):

Imagen basada en python:3.11-slim.

Utiliza la variable de entorno PYTHONPATH=/app.

Seguridad de Red: El puerto 8000 del contenedor está mapeado EXCLUSIVAMENTE al localhost del servidor (127.0.0.1:8000:8000). No responde a peticiones externas.

Base de Datos (MySQL 8.0):

Seguridad de Red: No tiene puertos mapeados hacia el exterior de ninguna forma. Solo puede ser accedida por el backend a través de la red virtual interna de Docker (tonalkab_net).

Persistencia garantizada mediante un Docker Volume nombrado db_data.

Cuenta con un healthcheck nativo que bloquea el arranque del backend hasta que el motor InnoDB esté 100% operativo.

3. Enrutamiento y Proxy Inverso (Nginx)
El único punto de entrada público a la aplicación es el demonio Nginx instalado directamente en el host (no dockerizado). Toda la API responde exclusivamente bajo el subdominio asignado: api.tonalkab.com.

Archivos de Configuración: Las reglas están definidas en /etc/nginx/sites-available/ y enlazadas a sites-enabled/.

Cifrado SSL/TLS: Se gestiona mediante Certbot (Let's Encrypt). Nginx intercepta todo el tráfico que llega al puerto 80 y aplica una redirección automática HTTP -> HTTPS (puerto 443). Las renovaciones de los certificados están automatizadas.

Lógica del Proxy: Cuando una petición validada y cifrada llega a https://api.tonalkab.com, Nginx actúa como Reverse Proxy (mediante la directiva proxy_pass) y empuja el tráfico internamente hacia http://127.0.0.1:8000 (donde escucha el contenedor de FastAPI).

4. Directorio y Estructura de Archivos
La disposición física en el disco duro del usuario tonalkab está estrictamente organizada:

~/tonalkab-backend/: Directorio raíz del proyecto. Contiene el código fuente en Python, la subcarpeta app/models/ (donde residen las definiciones de SQLAlchemy para las 16 tablas del sistema, incluyendo usuarios, macetas, sensores, etc.) y el archivo docker-compose.yml.

~/tonalkab-backend/.env: Archivo de variables de entorno donde residen las credenciales críticas de la DB y el SECRET_KEY de JWT. No versionado en Git.

~/scripts/backup_db.sh: Script ejecutable en bash diseñado para extraer volcados SQL mediante mysqldump desde dentro del contenedor MySQL.

~/backups/mysql/: Almacén local donde se guardan los archivos comprimidos .sql.gz del histórico de la base de datos.

Automatización Cron: Existe una tarea en el crontab del sistema que despierta todos los días a las 3:00 AM para ejecutar el script de respaldo de forma silenciosa.

5. Arquitectura de Autenticación
Usuarios Finales: Se manejan mediante tokens JWT con tiempo de expiración. Se tiene integrado el proveedor google-auth para inicio de sesión de terceros (tabla auth_providers).

Dispositivos IoT (ESP32): El ecosistema de macetas inteligentes (las cuales operan bajo un principio de generación de energía por biomediación/descomposición de microorganismos) se comunica con el backend mediante un API Key único generado con secrets.token_urlsafe(32) y validado contra un hash criptográfico SHA-256 en la base de datos.

REGLA DE ASISTENCIA: Cualquier recomendación de arquitectura, nuevo endpoint o modificación al docker-compose debe asumir que la base de datos MySQL debe permanecer completamente oculta al exterior, y que FastAPI solo puede comunicarse con el exterior a través del puente configurado en Nginx hacia 127.0.0.1:8000.
